## 二、前史：需求从哪来（2026-09-21 ~ 10-10）

**为什么做这个插件**：新业务域接入团队本体引擎，传统方式是"数周手工建模"。目标是把它压缩到"半天人审"——LLM 产草稿，人只做审核决策。

三个来源汇成共识：

1. **楠总 × Codex 会话（09-21~24）**：WorkBuddy 侧 FDE Plug-in 完整蓝图，贡献了产品契约——OntologyProposal 数据格式、变更集级写接口契约（preview→apply→validate）、"AI 只产草稿，人工审核是唯一权威"的红线。
2. **09-24 ZCode 调研报告**：LinkML / CQ 能力问题 / Palantir No-exceptions 规则落 lint / 插件结构，贡献了方法论与选型。
3. **10-10 需求明确化**：需求从"从零设计、不复用引擎"演进为"**导入既有 MCP 引擎**"（fnb 15 实体只读 + mfg 10 实体带沙箱，共用同一元数据 schema）——这一步决定了后面所有版本的核心矛盾：**我们的 DSL 必须与真实平台对齐，而不是自说自话**。

当天还澄清了本质定位（10-13 用户确认）：做的是"面向自家引擎的**本体元数据设计专家**"，不是学术本体工程——OWL 导出降为按需附件、不引入推理机、校验全部交给确定性 lint。产物收敛为：DSL YAML + 引擎注册格式 + 拓扑图。

贯穿全程的五条设计原则（不可违背）：人工审核唯一权威；机器可判定的校验全交确定性工具；写入走 preview→确认→apply；CQ（能力问题）驱动建模反推最小本体；不脑补、缺失信息显式列为待确认问题（provenance + open_questions）。

## 三、M0 POC：先验证三假设再动工（2026-10-13，版本 0 期）

**为什么**：方案的最大风险是"LLM 生成本体的质量"和"DSL 能否无损对接引擎"，这两个不验证就开发等于赌博。M0 用 1~2 天做 POC，三假设全部通过：

| 假设 | 结论 | 关键证据 |
|---|---|---|
| DSL 能无损表达既有本体 | ✅ | fnb 全量（15 实体/157 属性/24 links/60 规则）逆向导出再编译回去，round-trip **差异 0**，字节级复验一致 |
| LLM 生成质量够用 | ✅ | 合成域盲测：实体/字段/links/trigger/CQ 零漂移，**两处比人工 gold 更正确**（与引擎实际一致）——DSL 规范的约束把生成侧推向了正确方向 |
| 编译器可行 | ✅ | 纯结构驱动、零实体名特判，支持复合主键等全部 fnb 实测形态 |

**发现的问题与解决**：

- **三个规范缺口（都在规范侧，非生成侧错误）**：方言 cookbook 缺失（引擎 `COALESCE(x/y, 9999)` 惯例没写进规范，生成侧只能保守兜底）、多跳反向聚合语法未定义、upstream 语义不明 → 全部固化成 **DSL v0.2 修订清单 6 条**，M1 前执行完毕。
- **盲测意外收获**：生成侧交叉审查抓到资料包内部（rules.md 全量口径 vs decisions.md 本期口径）的真实冲突 + 4 条人工未察觉的问题——证明"provenance 三源交叉标注 + 禁止脑补"的纪律真实生效。
- **环境故障**：POC 期间 fnb MCP 端点连续 502 → 不降级不硬凑，改用 09-30 落盘缓存快照，并用 10-10 亲手拉取的一手元数据做**锚点验证**（5 组特征点全部一致，快照可信）；10-14 端点恢复后复拉复跑，字节级零差异，遗留关闭。

M0 奠定的工作纪律后来贯穿所有版本：**主代理独立复跑验证、字节级复验、不以子代理汇报为准**。

## 四、0.1.0（10-13）：插件骨架与最小闭环（M1）

**为什么**：POC 通过后立即插件化，把验证过的脚本资产装进 ZCode 插件形态。一天内完成：

- DSL v0.2 规范、`brief-intake`（资料包摄取）与 `ontology-modeling`（建模主技能）两个技能、插件清单与本地市场目录，**M0 全部验证资产随仓保留为对账锚点**（`poc/`）。
- 同日迁移脚本工具链：lint（8 条规则）/ render_topology / check_cq / compile，全部经字节级回归验证；附 fnb seeds 速查；dsl-spec 按实证修订 3 处。
- **第一次真人试用就暴露问题**：SKILL 没写清脚本在哪、产物放哪 → FDE 找不到脚本、产物散落一地 → 修复为"脚本定位 + 产物根目录确认"显式规则。这是"提示词也要做防呆设计"的第一个教训。

## 五、0.3.0（10-14）：M2/M3 能力完整版（0.2.x 号段未发布）

**为什么**：M1 只是骨架，质量与导入能力在 M2/M3 补齐，完成后统一升版 0.3.0：

- **M2（质量与导入）**：变更集 diff（JSON Patch + breaking 标记 + 版本冲突拒绝）；`ontology-review` 独立评审技能（12 项 checklist）；**studio-model 互导**——用真实 fnb 平台模板做编译测试，P0 问题全检出（lint 有效性的一次实战证明）；evals 回归体系建立（首批 7 项）。
- **M3（动作与平移）**：dsl-spec §4 动作规范定稿——关键决策是"**动作 body 是 Python 源码，无法声明式生成**"，DSL 只生成元数据 + 三种 recipe 配方骨架（mfg 8 个真实 action 实测归纳），人工插桩；`gen_action_skeleton.py`（骨架 py_compile 可过 + TODO 标记）；lint 第 10-11 条 admission 一致性检查；行为测试 case5（越权 4 话术全拒）/case6（错误建模陷阱资料包）；**WorkBuddy 侧镜像平移**（quickPrompts + 总控提示词含楠总蓝图红线原文 + 三技能镜像）。
- **端到端复验**：极米 xgimi 四场景本体——26 实体/234 属性/18 规则/12 CQ，lint 0 错、CQ 全解析、双格式编译通过；对照此前 21 实体基准，+5 实体全部有文档出处（防脑补可审计）。

**如实记录的遗留**：变更集 MCP 写接口依赖平台排期（契约已冻结，一期用文件导入绕行）；lint_model.py 329 行超代码规范上限（架构取舍：lint 规则集中单文件，记录在案）。

## 六、0.3.1（10-14）：DSL v0.3——实战打出来的第一版规范升级

**为什么**：xgimi 实战 + fnb 双载体对照，暴露了 DSL v0.2 表达力与治理缺口：

- links 不支持显式外键（复合外键无法表达）→ v0.3 增加显式 fk 形态；
- 规则命名无治理 → lint 增至 12 条：**规则名全局唯一 + 受控词表 glossary**；
- studio-model 编译支持 fk（复合外键告警跳过并登记）。

**发现的问题**：对照 fnb yaml 设计稿 vs MCP 实现注册表，产出两份对照报告——41 处规则重名，根因定位为**引擎实现扩展时丢失了消歧后缀**；差异三分类（合理扩展/实现错误/演进不同步）如实暴露转交引擎侧修订（`docs/fnb-yaml-vs-mcp-comparison.md`、`fnb-engine-fix-handoff.md`），插件不越权代改。行为测试 case3/5/6 实跑 3/3 PASS（冲突登记不擅自定稿/越权话术全拒/伪对象零命中）。evals 增至 18 项。

**这个版本确立的态度**：发现别人的问题，如实暴露、定位根因、转交处理，不静默兜底。

## 七、0.3.2（10-15）：定位校准——产品到底是什么

**为什么**：这是全项目**最重要的一次方向修正**。实战使用后发现：用户（FDE/业务方）拿到 engine JSON 没有直接用处——

> 两大核心交付物是**给人看的拓扑图（topology.png/svg）+ 给导入用的 yaml（studio-model.yaml）**，engine JSON 降为可选导出。

配套落地拓扑图 PNG/SVG 图片输出：Playwright + mermaid@11 无头渲染，CDN/本地缓存双路径、断网**不静默降级**（明确报告），diff 模式同样支持，既有行为字节级回归一致。

**教训**：我们按蓝图造了"导入工具"，用户实际需要的是"沟通工具 + 导入文件"。定位以产出首位排序的方式固化进主技能。

## 八、0.3.3（10-15）：平台导入校验修复——平台是规范源

**为什么**：生成的 yaml 导入平台时被拒。实测发现 `link_types.name` 必填非空，而 DSL 侧没有此约束。

**解决**：dsl-spec §8 更新（显式 name 键 + 编译器兜底目标实体中文名），39/39 非空验证通过，18 项回归全 PASS。

**教训（本版本的真正产物）**：从此确立"**平台实测行为是规范权威**"——规范不是抄文档写出来的，是拿平台校验出来的。

## 九、0.3.4（10-15）：导入后对账闭环——发现"平台会漂移"

**为什么**：复盘会话历史发现两个盲区。其一，导入成功 ≠ 导入正确：首跑 `check_platform_sync`（DSL↔平台 SDK 四维比对：实体/字段/主键/关系）就抓到 **Material 主键在平台侧已被改为 material_code，而源 DSL 毫不知情**——单向"生成→导入"不够，必须有双向对账。

**解决**：主技能补第 8 步"导入后自检闭环"（平台 SDK 存证 + check_platform_sync 复验零差异）；Material 主键修订写回 DSL（外键侧以 13 处显式 fk 声明承载，保持可审计）；evals case9 平台一致性回归（冻结夹具零差异 + 人为漂移可检出）。其二，brief-intake 引导后用户流失 → 补"最小可跑路径"纪律：任何资料状态下都能开工，不因缺文档卡死。

## 十、0.3.5（10-15）：关系语义名——用户一句实证顶十条规范

**为什么**：用户看拓扑图时实证发现——**只建了 link，但没人说清"这是什么关系"**。39 条关系全部无名，图上连线不可读，业务方无法审。

**解决**：dsl-spec v0.3.4 将关系 `name` 定为建模必填纪律 + lint 第 13 条；xgimi 39 条关系逐条命名（换算物料/订购物料/隶属项目……）+ 拓扑连线加语义标签 + 图片重出。显式形态下 fk 可缺省（由 name 承载语义）。

**教训**：机器校验管得住"有没有"，管不住"看不看得懂"——可读性是给人审用的核心质量维度。

## 十一、0.3.6（10-15）：设计稿硬关卡——把人审提前到 DSL 之前

**为什么**：用户提议流程重构。此前流程是直接生成完整 DSL 再让业务方审——业务方看不懂 YAML，等发现设计偏差时改动成本已经很高；同时对齐了楠总蓝图的 OntologyProposal 理念：**先审提案，再审实现**。

**解决**：九步流水线在确认点②插入 **design-proposal.md 硬关卡**——实体/关系/规则/CQ 呈审表格模板 + 骨架拓扑图，**未过确认点②禁止生成完整 DSL**。首跑（xgimi-rebuild）当天收集 8 条实战反馈全部落地：assumptions 独立节、编号规则（E/R/RU）、可空基数记法、骨架 fk 升级说明、fact-cards 载体明确、合并呈审变体条款。

## 十二、0.3.7（10-16）：呈审材料包——让业务方看得下去

**为什么**：两个反馈驱动。其一，用户反馈 classDiagram 密集难读 → 拓扑分层混合布局（flowchart subgraph 按实体 layer 分五层 + 语义名连线）；进而交互式拓扑产物化（自包含 HTML：分层 + 点击聚焦 + 关系名开关 + 同对多标签错位防重叠，浏览器直接打开、不依赖宿主）。其二，把"呈审材料包"明确进 SKILL：交互式 + 静态图双产物，CQ 三态勾选组件（有 Gen UI 环境增强 / 无环境降级 MD）。

**同期重大平台发现**：xgimi-rebuild 新流程首跑（25 实体/49 关系/13 规则）后导入平台实测（workspace 999），发现 **平台连线模型不支持复合主键**——11 个复合主键实体 6 处连线被跳过。解决：平台实证写入规范（dsl-spec §8：1 侧主键锁定自动填充 + N 侧单外键必填 + 复合主键连线不支持），主键规范改为**禁复合主键**（Palantir 单列路线，平台先例 list_id），xgimi-rebuild 完成 11 实体单列化改造，6→0 连线跳过、49/49 恢复。另将"关系三态判别"（连线/关系实体化/单列主键化）写入 modeling-guide，源于用户的一次概念辨析——防止把"连线表达受限"误判为"需要实体化"。

## 十三、0.3.9（10-19）：OQ 生命周期 + FDE 手册（0.3.8 号段空缺）

**为什么**：xgimi-rebuild 与旧版两版拉通定稿（1.0.0-draft.1，7 条裁决）过程中，暴露三类管理问题：

1. **关系有名字但没定义**：用户发现所有关系 description 为空——名字解决"叫什么"，定义解决"业务上意味着什么"。→ dsl-spec links 加 description 键 + 编译器读取（顺带修了 link_pair 三处解包遗漏）+ lint 13b；49/49 关系补写业务定义（此项原排 0.3.8，与 OQ 沉淀合并发布）。
2. **规则抽取有盲区**：两版对照实证——触发规则的密集区不在正文公式段，而在异常处理描述里。→ SKILL 第 2 步增加"异常语义强制扫描区 + 映射表"；CQ 变化响应型强制 ≥3 条（作为 trigger 覆盖探针）；设计稿规则表必附"异常处理段核对栏"——防"批准了一份不完整的清单"。
3. **Open Questions 管理散乱**：问过什么、谁裁决的、结论是什么没有留痕。→ OQ schema 固化进 dsl-spec（四态生命周期 + resolution 留痕）；SKILL 增加 OQ 生命周期纪律与问询单生成；`business-inquiry-template` 模板从 xgimi 实战提炼（零技术门槛四要素：问什么/为什么/影响/期望答复，FDE 可直接转发业务方）；旧版 12 条裁决全部映射同步到 rebuild 编号体系。

同时产出 `docs/user-guide.md` 完整使用手册（三种用法/三个确认点/产物说明/平台自检/FAQ）——插件的第一个"用户文档"，标志产品从"能用"走向"可交付"。

## 十四、0.4.0（10-19）：资产体系化——从工具到资产飞轮

**为什么（用户提议）**：此前每接一个新域都从零开始，且域定稿后的知识不沉淀——上一个域的术语、实体经验对下一个域毫无复用。解决为两条闭环：

1. **资产目录自动初始化**：空白场景安装插件即可开工，brief-intake 自动生成 `models/<domain>/` 标准资产树，零手工准备；
2. **域定稿资产回流**：定稿后自动生成 glossary 命名登记（重跑/增量自动复用，防命名漂移）+ seeds 域速查（跨域对齐的资产参照）——**种子随使用进化，越用越厚，下一个域"起点不为零"**。

仓库 README 重写为"资产三类分离"（发布产物/种子资产/运行资产）与流转规则图；分发节明确**分发单元 = 插件目录自包含**（manifest+技能+脚本+种子+离线缓存，非整仓）。WorkBuddy 镜像全量同步并打包 `aquilair-fde-0.4.0.zip`。

**镜像侧的教训（10-19~20 收尾）**：首次打包即被平台规范拦截——缺必填头像 `avatars/expert.png`、categoryId/email/defaultInitPrompt 不对齐官方规范、agents 总控提示词缺 frontmatter description（平台激活判据）。两天三次修复后确认：**镜像不是复制粘贴，目标平台的格式规范要用"装机实测"验证，与本体侧"平台是规范源"是同一条教训**。
