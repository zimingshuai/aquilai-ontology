# 摄取判型规则（intake-rules）

> brief-intake 技能的判型细则：文档 → A/B/C/D 类的判定依据与边界案例。

## 判型决策表

| 信号（按优先级） | 判型 | 归位 |
|---|---|---|
| CREATE TABLE / 主题/字段/类型 三列表格 / "数据字典"字样 | **A schema** | A_schema/ |
| 决策场景（谁/依据/做什么/KPI）、口径算法（"XX = …"）、流程/制度/状态流转/审批链 | **B scenarios** | B_scenarios/（decisions / rules / processes 三分） |
| 访谈记录、会议纪要、口述整理、微信群聊天记录导出 | **C interviews** | C_interviews/ |
| 既有本体导出 JSON（get_meta_* 返回）、行业参考模型（GS1/SCOR 摘录）、竞品功能清单 | **D reference** | D_reference/ |

## 边界案例裁定

1. **Excel 同时含字段表与口径说明列**：按字段表判 A 类；口径说明列在源摘要中显式标注"含口径"，建模阶段从 A 类材料中一并提取。
2. **需求文档混杂**（既有业务目标又有系统字段清单）：整份归 B 类（业务文档优先），源摘要标注"内含字段清单（第 X 节）"；不强行拆分用户文档。
3. **PPT/投标材料**：归 D 类参考材料（通常是愿景与功能面，不是可建模口径）。
4. **既有本体快照**（get_meta_objects 返回的 JSON）：归 D 类，命名 `existing_ontology.json`——增量建模时它是 diff 基准。
5. **同一文档多主题**（对账 + 库存两个场景）：归位后标注「跨场景」，提请用户确认是否拆成两个资料包（两个本体）。
6. **说不清的**：`待人工裁定` 区（intake-log.md 中列出），禁止按文件扩展名猜。

## brief.yaml 生成规则

```yaml
domain: <kebab-case>          # 与用户确认的场景标识
scenario_name: <string>       # 业务场景名（中文）
business_owner: <string>      # 业务负责人（从文档署名/访谈对象推断，须确认）
target_engine: fnb|mfg|new    # 增量建模选既有引擎；从零建库选 new
source_systems: [<string>]    # 来源系统清单（SRM/WMS/ERP…，从文档推断）
known_conflicts:              # 冲突预检结果；建模阶段未裁决不得定稿
  - { topic: <string>, side_a: <定义+来源>, side_b: <定义+来源>, status: pending }
```

## 缺口报告检查单（理想资料包对照）

| 检查项 | 缺失影响 | 建议话术（向用户要什么） |
|---|---|---|
| 无 DDL | 表结构只能从字典/口述推断，主键类型存疑 | "能否从 XX 系统导出建表语句？" |
| 无数据字典 | 字段业务含义缺失，语义标注层质量降 | "能否补充字段口径说明（哪怕 Excel 一列备注）？" |
| 无决策清单 | CQ 无从提炼，建模范围失焦 | "业务上要用这个本体回答哪些问题？谁用？" |
| 无口径规则 | derived 规则无法生成 | "现有报表里这些指标怎么算的？" |
| 单一来源（只有口述） | 三源交叉验证缺失，冲突无法暴露 | "能否再给一份书面材料交叉验证？" |
