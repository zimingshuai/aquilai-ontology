# 场景章程模板（charter）——确认点①的呈审材料

> 用途：第 1 步产出、确认点①由用户确认的**场景章程**。纯自然语言+表格——审阅人不需要懂任何 DSL/格式规范就能逐节审。
> 承接：读 brief.yaml（含 `exploration_record` 指向的探索记录）。有探索记录时，本章程的「必问收口清单」与探索记录阻塞清单逐条对应——Charter 是必问项的收口现场。

## 模板结构（复制到 models/<domain>/charter.md 使用）

```markdown
# <域名> 场景章程（Scenario Charter）

> 产出步骤：ontology-modeling 九步流水线第 1 步 ｜ 状态：<draft（待确认）| confirmed（确认人/日期/结论）>
> 来源资料包：`models/<domain>/modeling-brief/`（<主要材料一句话>）
> 探索记录：`models/<domain>/modeling-brief/exploration.yaml`（<check_exploration.py 判定：可交接 / 阻塞项已列入第二节>）｜ 无探索记录时本行写"无"

## 一、Scenario Charter
| 要素 | 内容 | 出处 |
|---|---|---|
| 业务目标 | <一句话：这域要达成什么> | <资料包路径#位置 / 探索条目 X-NNN> |
| 触发事件 | <什么发生了才开始处理> | |
| 决策对象 | <要做出的决策或产出> | |
| KPI 或损失基线 | <衡量指标；没有 KPI 时写现状损失> | |
| 参与角色 | <谁提供数据、谁使用结果> | |
| 审批边界 | <哪些结果需要人批准才能生效、哪些不自动外发> | |
（六项要素不得缺；可按需增行，如"范围排除"）

## 二、必问收口清单
（来源：探索记录阻塞清单——必问项且尚未获用户明确答复的条目。**Charter 确认时逐条批复**：用户在勾选呈审页选"按建议 / 改为 / 否决"并复制批复文本回贴，批复经 `apply_exploration_feedback.py` 写回探索记录，`check_exploration.py` 阻塞为 0 才能进入抽取。用户在对话中逐条明确答复的，同样转写为批复行经脚本写回，以门禁结果为准。无探索记录或阻塞清单为空时写"无"。）
| 编号 | 陈述 | AI 建议 | 当前状态 | 批复 |
|---|---|---|---|---|
| X-NNN | <用业务语言写的问题与现状> | <可直接采纳的建议答案；备选及影响> | proposed / pending | 按建议 / 改为：… / 否决：… |

## 三、建模设计红线
| 红线 | DSL 落点 | 出处 |
|---|---|---|
| <必须体现在设计里的一条约束> | <落在哪个实体/属性/规则/动作上> | <资料包路径#位置 / 探索条目 X-NNN> |

## 四、能力问题 CQ
（写法与数量口径以 `skills/ontology-modeling/references/cq-guide.md` 为唯一事实源；用户与资料都没提时按其"主动补缺"规则办，AI 建议的条目标注"AI 建议（待确认）"。）
| id | 问题（业务语言） | 类型 | 来源 |
|---|---|---|---|
| cq-001 | <这个本体能回答的一个业务问题> | 范围型 / 验证型 / 变化响应型 | <资料包路径#位置 / 探索条目 X-NNN / AI 建议> |

## 五、边界声明
- <计算类超方言能力如何登记（运行时契约 / open_question）>
- <流程步骤不建对象；预测/优化语义不进本体>
- <本章程为 draft 版，按"人审是唯一权威"原则待人审确认后生效>
```

## 呈审与确认纪律

1. **逐节呈审**：按 Charter 表 → 必问收口清单 → 设计红线 → CQ → 边界声明 顺序引导审阅人过一遍，不一次甩全量。
2. **必问收口是硬前置**：有探索记录时，进入第 2 步抽取的前置条件是 `python scripts/check_exploration.py <exploration.yaml>` 判定可交接（阻塞清单为空）。阻塞清单非空时把阻塞项原样列进第二节呈审，**不得带着未收口的必问项开始抽取**。
3. **收口批复走脚本**：批复来自勾选呈审页（`render_explore_checklist.py` 生成）的"一键生成批复文本"，经 `python scripts/apply_exploration_feedback.py <exploration.yaml> --feedback <批复文本文件> --by <确认人>` 确定性写回并自动复检；禁止手改探索记录的状态来代替用户批复。
4. **确认后才抽取**：Charter 未经用户确认不进入第 2 步；Charter 被驳回回本步修订后重新呈审。确认结论（确认人 / 日期 / 结论）写进文件头的状态行，时间一律 bash `date +'%Y-%m-%d %H:%M:%S'` 现场取。
5. **合并呈审变体**：Charter 与设计稿一并呈审时，两项分别批复——必问收口清单随 Charter 批，不与设计稿确认混为一次。
6. **对照范例**：实物范本见 `examples/supplier-recon/`（插件根）中的第 1 步产物，起草前先对照。
