# 能力问题（CQ）指南

> CQ = Competency Question：「这个本体能回答哪些业务问题」。一物三用：建模前的**需求规格**、建模后的**验收用例**、技能迭代的**回归测试**。证据链：本体工程 20 年主流评估法 + Palantir 决策驱动设计（CQ 的企业版 = 决策 + 依据信息）。

## 一、写法规则

1. **业务人员的语言**，不是技术语言：问"哪些 SKU 在哪些仓库的库存低于安全线？"，不问"哪些 SKUInWarehouse 记录的 onhand_inventory_qty < safety_stock？"。
2. **可验证**：每条 CQ 必须能映射到具体 DSL 元素（covered_by），建完可逐条回验。
3. **数量 5~10 条**：少于 5 条范围圈不住；多于 10 条说明场景太大，应拆分。
4. **来源可溯**：每条 CQ 注明来自哪份材料（决策清单/访谈），无来源的 CQ 是脑补信号。
5. 覆盖两类：**范围型**（圈定本体边界——这个域管什么）+ **验证型**（关键口径的试金石——最复杂的业务问题必须能回答）。

## 二、分类模板（从决策清单推导）

| 决策句式 | CQ 模板 | 示例 |
|---|---|---|
| 谁需要看哪些对象的状态 | 哪些 <实体> 满足 <条件>？ | 哪些对账单差异金额超阈值且差异率超阈值？ |
| 某对象的完整画像 | <实体> 的 X/Y/Z 分别是多少？ | 某供应商本期发票金额、已对账金额、差异金额？ |
| 跨对象追溯 | <实体A> 名下所有 <实体B> 的合计？ | 某供应商名下所有交货记录的金额合计？ |
| 异常识别 | 哪些 <实体> 处于 <异常状态>？ | 哪些供应商处于冻结状态？ |

## 三、covered_by 填写规则

- 格式：`<Entity>` 或 `<Entity>.<field>`；可多值。
- 覆盖 = CQ 的答案可由这些元素（配合查询）得出；derived 字段填其目标字段（如 `ReconciliationStatement.recon_diff_amount`）。
- check_cq.py 校验 covered_by 引用可解析性；语义覆盖度由人在评审时终审（机器只查引用合法性）。

## 四、CQ 与流水线的钩子

- 第 1 步（场景圈定）：从 B_scenarios/decisions.md 提炼初版 CQ → 用户确认。
- 第 5 步（CQ 回验）：check_cq.py 产出覆盖矩阵 → 未覆盖 CQ 的处理二选一：补 DSL 元素（记录到 model.yaml）或修改/删除 CQ（须用户确认，并回写决策清单）。
- 人审门：评审报告必须附 CQ 覆盖矩阵——"本体能回答什么"是评审的第一问。
