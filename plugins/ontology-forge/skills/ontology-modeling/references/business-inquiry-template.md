# 业务问询单模板（business-inquiry）——OQ 能力沉淀产物

> 用途：把 pending-business 类 OQ 汇总成业务方零技术门槛可答的问询单——每条带 AI 建议答案与备选，业务方可以直接回"按建议"；FDE 直接转发。
> 实战样例：`examples/supplier-recon/business-inquiry.md`（插件根）。

## 模板结构（复制到 models/<domain>/business-inquiry.md 使用）

```markdown
# <域名> 业务问询单（FDE 可直接转发业务方/文档作者）

> 生成：<日期> ｜ 来源：<域名> 定稿（<版本>）open_questions 中 N 条 pending-business
> 用途：回复后由 FDE 交回建模侧补 DSL 出终版
> 说明：每条按【问什么 / AI 建议答案 / 备选 / 为什么问 / 影响 / 期望答复】组织，业务方无需了解本体技术；同意建议直接回"按建议"

---

## Q1. <一句话问题>（OQ-XX）

- **问什么**：<业务语言的问题>
- **AI 建议答案**：<具体到可直接采纳的答案——不写"建议结合实际情况决定">
- **备选**：<备选 1：内容及其影响>；<备选 2：内容及其影响>（1~2 个，写清选它和选建议的差别）
- **为什么问**：<这个问题如何影响建模/计算口径——用业务因果说，不用技术术语>
- **影响**：<不回复的后果：枚举不全/口径不准/字段缺失等>
- **期望答复**：<回"按建议" / 选备选 N / 给出自己的答案（清单/截图/字段表/一句话）>

（逐条同样式）

---

**已解决无需询问的**（供参考，避免对方重复操心）：<已解决/等引擎类一句话罗列>
```

## 纪律

1. **零技术门槛**：问题与建议里不出现 DSL/实体/links 等术语——业务方看到的是业务问题不是建模问题。
2. **每条要素齐全**：问什么 / AI 建议答案 / 备选 / 为什么问 / 影响 / 期望答复——缺"AI 建议答案"业务方只能开放式作答、无法回"按建议"；缺"影响"业务方无法判断优先级。
3. **每条各有建议**：AI 建议答案具体到可直接采纳；只列备选不指推荐、用"建议结合实际情况决定"代替结论、多题只给一个笼统建议，均属违规。
4. **未决也必须留建议**：追问两轮仍无答复的条目照样带着 AI 建议答案与备选留在单上（status 保持 pending-business），不得退化成只记录问题标题。
5. 只收 pending-business 类；pending-engine 类放末尾"已解决无需询问"参考区（不占对方时间）。
6. 回复回流：答复进 OQ 的 resolution（注明业务方答复原文+日期），DSL 补改后 status → resolved。
