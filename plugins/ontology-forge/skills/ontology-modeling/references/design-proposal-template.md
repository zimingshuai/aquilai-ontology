# 设计稿模板（design-proposal）——确认点②的呈审材料

> 用途：第 3 步产出、第 4 步 FDE 确认的**本体设计提案**。纯自然语言+表格——FDE 不需要懂任何 DSL/格式规范就能逐表审。
> 对齐楠总蓝图 OntologyProposal 理念：先提案、确认、再形式化为 DSL。确认前的修改成本最低。

## 模板结构（复制到 models/<domain>/design-proposal.md 使用）

```markdown
# <域名> 本体设计提案（design-proposal）

> 版本：<N>-draft ｜ 呈审人：FDE（agent）｜ 待确认人：____
> 确认记录：____（确认人/日期/修改意见摘要——每次返改追加一行）

## 一、场景回顾（一段话 + CQ 清单）
（Charter 已在确认点①定稿，这里只放摘要供对照：业务目标一句话 + N 条能力问题编号）

## 二、实体设计（共 N 个）
| # | 实体（英文） | 展示名 | 主键 | 关键字段（≤5 个，含类型） | 一句话职责 | 来源 |
|---|---|---|---|---|---|---|
| 1 | PurchaseOrder | 采购订单 | purchase_order_nr | 订单日期 DATE / 订单总量 DOUBLE / 状态 STRING | 已确认未收货的在途采购承诺 | DDL.purchase_order |
（每个实体一行；字段只列业务关键字段，不必全量——全量在 DSL 阶段落）

## 三、关系设计（共 N 条）——说清"是什么关系"
| # | 从 → 到 | 关系语义名 | 基数 | 业务含义（一句话） | 来源 |
|---|---|---|---|---|---|
| 1 | 采购订单 → 物料 | 订购物料 | n:1 | 每张订单订购一种物料 | DDL 外键 material_id |
（语义名即 DSL links 的 name / 拓扑连线标签——审表人重点看这列是否说清关系）

## 四、规则设计（共 N 条）
| # | 类型 | 名称 | 口径（自然语言/公式） | 挂载实体 | 来源 |
|---|---|---|---|---|---|
| 1 | 衍生 | 库存周转天数 | 平均库存 ÷ 日出库量，异常记 9999 | SKU在库状态 | rules.md §x |

## 五、CQ 覆盖预映射
| CQ | 回答它需要的实体/关系/规则（引用上面表格的编号） |

## 六、待确认事项（open_questions）、口径冲突（conflicts）与生成假设（assumptions）
- open_questions：要人裁决的问题（问题/缺在哪份材料/建议）——**未裁决不得进 DSL 定稿**
- conflicts：口径冲突（双方定义+来源）
- assumptions：**生成假设**（可抽查的推断记录，如类型推断/结构取舍）——与 open_questions 是两类东西，假设不需要裁决但人审时可抽查推翻
## 编号规则（表间引用用）
实体 E01..En / 关系 R01..Rn / 规则 RU01..RUn / 能力问题沿用 charter 的 cq-NNN；CQ 预映射引用编号不引用全名
## 表格补充约定
- 实体表"关键字段"装不下的字段：在该行末尾"备注"注明"阶段⑤补全字段：…"（确认后机械形式化的字段清单依据）
- 关系表可空外键：基数列记"n:1（可空）"

## 七、骨架拓扑
（贴 topology-skeleton.png/svg；图上实体+连线+语义名标签，FDE 看图核对第二节/第三节的完整性）
```

## 呈审与确认纪律

1. **逐表呈审**：按 实体表 → 关系表 → 规则表 → CQ 映射 → 待确认事项 顺序引导 FDE 过一遍，不一次甩全量。
2. **修改回路**：FDE 意见 → 当场回改设计稿与骨架拓扑 → 重新呈审；每轮修改在头部"确认记录"追加一行。
3. **确认后才形式化**：确认点②通过前禁止生成完整 DSL（骨架 DSL 除外——仅实体+links+主键字段，用于画图）。
4. 骨架 DSL 命名建议 `models/<domain>/model.skeleton.yaml`（确认后升级为 model.yaml 或对照补全）。**骨架的 fk 字段缺口是预期状态**：骨架仅声明主键+名称字段，显式 fk 引用的外键字段在升级阶段⑤一次性补齐——不要对骨架跑 lint（fk 检查会按设计报错）。
