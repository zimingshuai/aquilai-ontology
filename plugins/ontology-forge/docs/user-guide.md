# Ontology Forge 使用手册（FDE 版）

> 适用版本：v0.6.0+ ｜ 更新：2026-11-26 ｜ 读者：FDE / 开发人员 / 首次使用的同事——照本手册从头走到尾，即可完成一次真实建模。

## 一、这个插件是怎么工作的

插件把「LLM 本体建模」拆成**三个技能 + 一组确定性脚本 + 一套门禁**。你不需要记住技能名——说什么话会自动触发对应技能：

```text
你的文档/口述
    │
    ▼
┌─ brief-intake（摄取技能）────────────────────────────┐
│ 文档判型归位（A/B/C/D 四类）→ brief.yaml 资料清单     │
│ → 完备度评分（0-10）→ 缺口报告 → 冲突预检            │
│ 零文档/有缺口 → 八维探索：少问且带建议问，            │
│   结论逐条落 exploration.yaml（探索记录）             │
└──────────────────────────────────────────────────────┘
    │  探索记录须过门禁（必问项全收口才放行）
    ▼
┌─ ontology-modeling（建模主技能）─────────────────────┐
│ 九步流水线：                                          │
│ ① 场景圈定(Charter+CQ)★确认 → ② 事实卡片抽取        │
│ → ③ 设计稿合成 ★逐表确认（硬关卡）→ ④ DSL 生成       │
│ → ⑤ 双层校验（L1 lint 20 条 + L2 语义沙盘，error 拦截）│
│ → ⑥ CQ 回验 → ⑦ 拓扑图+平台 yaml 交付               │
│ → ⑧ 平台导入与对账 → ⑨ 资产回流（glossary/域速查）  │
└──────────────────────────────────────────────────────┘
    │  人审门
    ▼
┌─ ontology-review（评审技能）─────────────────────────┐
│ 机器检查先行 + checklist 逐项评审 → 带证据报告  │
└──────────────────────────────────────────────────────┘
```

四条设计原则（贯穿全程，遇到疑惑按这个判断）：

1. **人审是唯一发布权威**——插件永远只产 draft（`-draft.N` 版本），三个确认点全在你手里；
2. **单一事实源**——`model.yaml`（DSL）是唯一权威，拓扑图 / 平台 yaml / 引擎 JSON 全部由它编译生成，改任何东西只改 DSL 再重编译；
3. **不脑补**——资料没说的进待确认问题（OQ），AI 的补全建议一律标「AI 建议」等你批复；
4. **机器拦确定性缺陷，人拦业务判断**——结构 / 引用 / 方言错误由 lint 与沙盘拦截，口径对不对由你审。

**质量不是口号是回归资产**：行为回归 `evals/ontology-modeling/run_evals.py`（46 项断言）+ 分发门禁 `check_dist.py`（90 项，含 lint 条数等数字口径的事实源联动断言）。改插件必跑；条数以各脚本实时输出为准，本文不写死。

## 二、准备

### 2.1 安装与 30 秒验证

| 平台 | 安装方式 |
|---|---|
| ZCode | Plugin Marketplace → Add → 指向 `plugins/marketplace.json` → 安装 Ontology Forge |
| WorkBuddy | 开放平台上传 `pack_workbuddy.py` 构建的 zip（见 `.codebuddy-plugin/README.md`） |
| Claude Code | `/plugin marketplace add <仓库>/plugins` 后安装 |
| Codex | `codex plugin marketplace add <仓库>/plugins` 后安装 |

装好验证：**新开会话**（旧会话不加载新版技能）发一句 `/onto 我有一份采购业务的需求文档，帮我建本体`——插件应开始引导你给文件。

### 2.2 运行环境

| 依赖 | 何时需要 | 安装 |
|---|---|---|
| Python 3.10+ 与 PyYAML | 必须（脚本工具链） | `pip install pyyaml` |
| rdflib + owlrl + pyshacl | L2 语义沙盘（缺失时报错退出，不静默跳过） | `pip install rdflib owlrl pyshacl` |
| Playwright + Chromium | 只要拓扑图 PNG 才需要 | `pip install playwright && python -m playwright install chromium` |

### 2.3 资料怎么准备（给业务方/自己收集时参考）

资料不要求齐全——**只有 DDL 也能开工**，缺什么会进缺口报告并引导后续补。理想资料包四类：

| 类 | 内容 | 建模价值 |
|---|---|---|
| **A 结构**（最强） | 建表 DDL、数据字典 | 表→实体、列→属性、外键→关系，确定性最高 |
| **B 场景** | 决策清单（谁/依据什么/做什么决策/KPI）、口径规则、流程制度 | CQ 与规则的来源 |
| **C 访谈** | 访谈记录、会议纪要、口述 | 术语与口径的交叉核验 |
| **D 参考** | 既有本体导出、行业模板、竞品清单 | 增量基线与命名参考 |

数据字典建议按简化 ISO 11179 整理（没有也不阻塞）：`table_name / field_name / business_term / definition / data_type / enum_values / pk / fk_target / source_system`。

## 三、场景 A：有资料的完整建模（主路径）

以下按步骤说明**每一步插件做什么、你做什么、产物落在哪**。产物统一在 `models/<域名>/`（首次触达新域时自动初始化标准资产树）。

### 3.0 摄取（brief-intake）

- **插件做**：逐份判型归位到 `modeling-brief/` 的 A/B/C/D 子目录（原件只读不动）；生成 `brief.yaml`（场景名 / 业务负责人 / 目标引擎 / 来源系统——逐项请你确认）；产出**完备度评分（0-10 四维：场景明确性 / 结构化基础 / 术语可核性 / 冲突已知度）**与缺口报告（缺什么、影响什么、建议找谁要）；多文档口径打架时写入 `known_conflicts` 请你裁决。
- **你做**：确认 brief.yaml 各项；按缺口报告决定是否先补料（低分只调建议强度，不阻塞开工）。

### 3.1 场景圈定（确认点①）

- **插件做**：读资料与探索记录，产出**场景章程**（`charter.md`：业务目标 / 触发事件 / 决策对象 / KPI / 参与角色 / 审批边界 + 建模红线 + **5~10 条能力问题 CQ**）；有探索记录时章程含**必问收口清单**。
- **你做**：逐节确认章程——特别是 CQ（这批模型要能回答哪些业务问题，建完逐条回验）与必问项批复。**章程未确认不进入抽取。**

### 3.2 术语与候选抽取

- **插件做**：产出**业务事实卡片**（`fact-cards.md`：实体 / 关系 / 规则候选表，每条带资料出处与置信度；含**异常语义→规则映射表**——资料里"异常处理/红线/附录限制"逐条登记，防漏抽；含**探索记录承接表**）。
- **你做**：不用逐条核（设计稿才是你的主审点），但可抽查出处真实性。

### 3.3+3.4 设计稿合成与确认（确认点②，**硬关卡**）

- **插件做**：合成**设计提案**（`design-proposal.md`：实体表 / 关系表 / 规则表 / CQ 映射 / 待确认事项——纯表格，不需要懂任何格式）+ **交互式拓扑图**（浏览器打开，点击实体聚焦邻接关系）+ CQ 勾选页；分批呈审（对象层→规则与联动层，小域合并一批）。
- **你做**：**逐表审**——这是最重要的纠错点，改这里最便宜。重点看：实体表"一句话职责"是否准确；关系表**"关系语义名"列**是否说清"是什么关系"（"订购物料"✓，只有"物料"✗）；规则表的**异常覆盖核对栏**；待确认事项（来自探索记录的 AI 建议都标了"未确认"）。
- **红线**：设计稿未确认，插件不会生成完整 DSL。修改意见当场回改重新呈审，确认留痕在头部。

### 3.5 DSL 生成与双层校验

- **插件做**：确认后的设计稿机械形式化为 `model.yaml`（DSL v0.4）；然后两道机器检查连跑——**L1 lint**（20 条确定性检查：命名 / 主键 / 关系闭合 / 表达式方言 / 规则名唯一 / OQ 结构 / 枚举双写 / 基数 / 分支触发 / 声明式动作 / 准入字段……）与 **L2 语义沙盘**（DSL 投影 OWL/SHACL 做语义自洽检查：派生承诺 / 外键类型 / 孤岛实体 / 孤儿动作，检完即弃）。**error 一律拦截**，warning 随产物呈审。
- **你做**：报错原文贴回对话即可，插件修复后重跑。**别要求跳过 lint**——那是质量闸。

### 3.6~3.8 CQ 回验与交付

- **插件做**：CQ 覆盖矩阵逐条验证（未覆盖的补元素或改 CQ 需你确认）；交付**两大核心产物**——`topology.png/svg`（拓扑图）与 `engine-bundle/studio-model.yaml`（**平台导入格式，直接对齐平台现行导入规范**：计算规则带关系路径、触发分支、校验挂载、声明式动作一步到位）。产物树：

```text
models/<域名>/
├── charter.md / fact-cards.md / design-proposal.md   # 过程产物（追溯）
├── model.yaml                    # ★ 本体 DSL（唯一 source of truth，进 git）
├── topology.png / .svg           # ★ 交付物①：给人看的拓扑图
├── engine-bundle/studio-model.yaml  # ★ 交付物②：平台导入 yaml
│   └── import-README.md          # 导入说明（含"需平台侧配置"名单，见 §5.2）
├── modeling-brief/               # 资料包（含 exploration.yaml 探索记录）
├── sandbox.*.ttl / report.md     # L2 沙盘存档
└── README.md                     # 域资产说明 + 任务日志
```

### 3.9 平台导入与资产回流

见 §5（平台对接）。域定稿后插件执行**资产回流**：实体命名登记 `seeds/glossary.md`（同域重跑自动复用命名，防漂移）、生成 `seeds/<域名>-entities.md` 域速查——**种子越用越厚，下一个域起点不为零**。

## 四、场景 B：零文档口述（探索记录工作流）

连文档都没有、只有口述（或资料有缺口需要你拍板）时，走**八维对话探索**，把问出来的规格当资料：

```text
D1 范围 → D2 对象·属性·关系 → D3 状态 → D4 动作 → D5 触发与联动
→ D6 计算口径与校验 → D7 数据源 → D8 能力问题
```

操作级流程：

1. **插件提问，你回答**——它遵守「少问且带建议问」：
   - **可补全项**（行业惯例、常见属性/类型）：AI 直接给建议，成批呈给你过，不逐项发问；
   - **必问项**（只有 6 条：联动及其失败语义 / 删除引用处理 / 状态迁移 / 口径与计量单位 / 术语特殊含义 / 动作写入风险）：逐条问，每问必带「AI 建议 + 理由 + 备选」，你回「按建议」即可。
   - 属性是探索主战场之一：属性清单/类型 AI 补全批量过；计量单位与换算、枚举取值全集、空值含义属必问。
2. **全部结论落 `exploration.yaml`**（条目带四态：confirmed / proposed / pending / rejected）——对话里说过不算数，落了记录才算。
3. **勾选确认**：插件生成勾选页（`explore-checklist.html`）——浏览器打开，按维度分组逐条勾（✅按建议 / ✏️改为 / ❌否决 / 选备选），点「生成批复文本」复制。
4. **批复回贴**：把批复文本贴回对话，插件经脚本确定性写回并自动复检（追问两轮仍不明确的条目保持 pending 并保留 AI 建议，不阻塞）。
5. **交接判定**：`check_exploration.py` 门禁——**必问项全部收口才可交接建模**；没收口的自动挂到场景章程「必问收口清单」，随确认点①一并批复。

注意：**完成规格对话 ≠ 资料齐了**——探索后照常出完备度评分与缺口报告；后续拿到任何文档（DDL/字典/链接）正常归位，评分自然升级。探索记录是 C 类弱佐证，定稿仍走设计稿硬关卡。

## 五、平台对接

### 5.1 导入

平台 → 项目管理 → 新建项目 → **上传 YAML**（选 `engine-bundle/studio-model.yaml`）→ 校验 → 创建。注意：平台无「重新导入」，yaml 更新需删除项目重建（项目 ID 会变）。

### 5.2 哪些东西不会随 yaml 进平台（如实在导入说明里列出）

- **函数型动作**：函数是平台侧代码包，不随 yaml 往返——导入后需在平台配置函数步骤（函数名与契约见 DSL）；
- **recipe 动作**（旧骨架形态）：需平台侧按骨架实现配置；
- **被规则引用但未在 DSL 声明的动作**（平台内置）：名单在 `import-README.md`。

### 5.3 导入后对账（两种平台侧输入）

```bash
python scripts/check_platform_sync.py models/<域名>/model.yaml <平台侧文件>
```

- 平台侧 = **工作区 SDK**（aquilair.py）：实体/字段/主键/关系四维比对；
- 平台侧 = **MCP 元数据 JSON**（`metadata_workspace_model` 的返回，裸六键或 JSON-RPC 包装均可）：四类对账（实体/关系含基数/规则/动作）。

平台手改当场现形（实战抓过主键被改）；差异按你的裁决写回 DSL。

### 5.4 从平台逆向（增量基线）

平台导出的 model.yaml（现行格式）可直接逆向为 DSL：

```bash
python scripts/export_dsl.py --platform-yaml <平台导出model.yaml> --output <dsl.yaml> --ontology <域名>
```

**往返保证**：编译→逆向→lint→再编译，产物字节一致（回归锁定）。平台不承载的信息（表名/别名/lookup 等）在产物的 assumptions 里逐条注记，需人工确认。

## 六、场景 C：增量建模（对既有本体做扩展）

说「基于现有 XX 本体，新增一个 YY 场景，只出差异」即触发：

- brief.yaml 的 `target_engine` 指向既有域 → 插件先读 `seeds/` 域速查与既有 DSL，**复用既有实体与术语，只建差异**；
- 产出**变更集**（`diff_model.py`：add/remove/replace + breaking 判定——删元素/改类型/改主键标 breaking 需你重点审）+ diff 版拓扑（新增绿/删除红/修改黄）；
- **版本冲突拒绝**：变更集基于的快照版本与当前不符时拒绝覆盖、要求重读重生成——不强推。

## 七、场景 D：评审既有本体（ontology-review）

说「检查/评审本体质量」「两版本体对比」「这个本体能支撑 XX 场景吗」即触发：

- 机器检查先行（lint/沙盘/CQ 不过直接打回）；
- 按 checklist 逐项评审（结构层粒度/孤立实体/关系质量；语义层口径正确性/术语一致性/OQ 清零/卡片↔DSL 一致性；应用层 CQ 语义覆盖/归属完整/方言边界/治理就绪），每项 ✅/⚠️/❌ **必须带文件+行号证据**；
- 结论（可合并/修后合并/打回）只是专业意见——**批准动作永远是人做**；评审不改文件。

## 九、团队用法：子代理派发（ZCode / Claude Code）

插件根 `agents/aquilair-fde.md` 随插件自动注册为子代理。主代理可派发建模任务，三条约定：

1. **确认关卡到达即停**——子代理无法与你对话，到确认点（Charter/设计稿/变更预览）即停，呈审材料交回主代理转呈；
2. **任务令须含起止步骤**（如"第 5~7 步：DSL 生成+lint+CQ 回验"）；**口述探索不派发**（必须与用户对话）——任务令须自带已可交接的 exploration.yaml；
3. **验收看产物、复跑脚本核对，不以子代理自述为准**（详见 `agents/README.md`）。

## 十、常见问题

**Q：lint 报错怎么办？** 把报错原文贴回对话，插件修复后重跑。lint 不过不进下一步是设计如此。

**Q：实体/关系名每次生成会不一样吗？** 域定稿后命名固化进 glossary；**同域更新走增量模式（§六），不要从零重跑**。

**Q：探索记录里"必问项"一直没收口，能继续吗？** 不能进抽取——这是防"猜错出业务逻辑错误"的硬闸。要么在勾选页批复，要么随章程确认点一并批复。

**Q：图片渲染报 Playwright 错误？** 装 §2.2 依赖；断网环境自动用插件内缓存（与 CDN 同版本）。

**Q：业务方迟迟不回问询单，能定稿吗？** pending-business 类 OQ 不能自动清零——要么等回复，要么评审时显式标记"接受风险"。问询单（`business-inquiry.md`）每条带 AI 建议与备选，业务方可直接回"按建议"。

**Q：产物落在了哪？** `models/<域名>/`（相对当前会话工作区）。若工作区不是专门的本体仓库，插件会先和你确认产物根目录。
